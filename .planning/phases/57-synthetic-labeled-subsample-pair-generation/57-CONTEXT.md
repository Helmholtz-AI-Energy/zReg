# Phase 57: Synthetic Labeled Subsample-Pair Generation - Context

**Gathered:** 2026-08-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Users can specify, via `transform_spec`, a labeled `(source, target)` dataset pair generated by subsampling a point cloud (real or freshly-synthesized) into two views with tracked per-point correspondence — a sibling mechanism to the existing known-transform (`transform_spec: rigid`/`noise`) path, usable by `EvaluationRunner`/`HyperparamOptimizer` for label-transfer HPO. This phase builds the generation mechanism and its config/HPO wiring; it does not add a train/val held-out evaluation capability (deferred, see below).

</domain>

<decisions>
## Implementation Decisions

### Reuse vs. Generalize `generate_training_triple`
- **D-01:** Build a **new** `DataFactory` method — not confined to `generate_training_triple()`'s ball/bowl-only geometry. The new method must accept an already-loaded `dict[int, zRegPointCloud]` (real data, e.g. from `load_real()`/`load_target()`, or a freshly-synthesized cloud) and produce a labeled `(source, target)` subsample pair with tracked per-point correspondence, reusing Phase 56's `_correspondence_idx`/`drop_points()` machinery rather than `generate_training_triple`'s fixed `sample_ball`/`sample_bowl` + `generate_labels` pipeline. `generate_training_triple()` itself is **unchanged** — Phase 46's training-data-generation contract stays intact; the new method is a sibling addition, not a replacement or refactor of it.
- **D-02:** The new method must still support the synthetic-from-scratch case (Phase 57's own scope explicitly includes "no real data available"), so it should accept either (a) an explicit dataset to subsample from, or (b) a shape/`n_classes`/`n_points` spec to synthesize one first via `sample_ball`/`sample_bowl`/`generate_labels` (i.e., it subsumes `generate_training_triple`'s synthetic-generation behavior as one mode, adding the real-data mode as another).

### Transform Application (conditional, not a new flag)
- **D-03:** Whether a rigid/noise transform is layered on top of the subsampling is **derived from `config.run_alignment`**, not a new user-facing config field:
  - `run_alignment=True` → subsample **and** apply a `transform_spec`-style geometric perturbation, so alignment has a genuine registration challenge to solve.
  - `run_alignment=False` (label-transfer-only runs) → subsample **only**; source and target stay in the same coordinate frame, so label-transfer accuracy isn't confounded by alignment error.

### Config Surface
- **D-04:** Exposed via a new `transform_spec` discriminator `type: "subsample_pair"`, sibling to today's `type: "rigid"` / `type: "noise"`, reusing the existing `pipeline_mode: synthetic` dispatch already present in `eval_runner.py` and `optimizer.py`. **No** third `pipeline_mode` value, **no** separate top-level `EvalConfig` field.
- **D-05:** Exact `transform_spec` key set for `type: "subsample_pair"` is left to planner discretion, but must cover: subsample size (e.g. `source_fraction`/`target_fraction`), `seed` (see D-06/D-07), and a way to select "subsample the already-loaded dataset" vs. "synthesize fresh ball/bowl geometry first" (per D-02).

### HPO Seed Strategy
- **D-06:** Default is **one fixed seed** (`transform_spec.seed`), used identically across every HPO trial in a run — exactly matching how `type: "rigid"`/`type: "noise"` already behave today (one fixed synthetic target scored by every trial). **No changes needed inside `HyperparamOptimizer._objective` for the default path** — this is a hard constraint, not just a preference, since it keeps trial-to-trial comparability intact (a per-trial-changing ground truth would inject noise the Sobol/Bayesian/TPE search strategies can't distinguish from genuine hyperparameter sensitivity).
- **D-07:** `seed` MAY optionally be a **list** of ints instead of a single int, in which case the trial's objective is averaged across the resulting N subsample pairs. This averaged path is **opt-in only** (not default) and must be gated so it isn't silently enabled for fast `sanity`/`dev` tiers (e.g. reject/warn when `len(seed) > 1` and `tier != "full"` — exact mechanism left to planner discretion).

### Train/Val Split — Explicitly Deferred
- **D-08 (deferred, NOT this phase's scope):** A train/val split for `subsample_pair`-generated ground truth (HPO searches against a "train" seed via `split_seeds()`-style disjoint seed derivation, a final held-out score is reported against a distinct "val" seed) was discussed at length. Confirmed by direct codebase check: `EvalConfig.val_split`, `DataFactory.prepare_split()`, and `split_seeds()` all exist but are **currently unused** by `HyperparamOptimizer`/`EvaluationRunner` — there is no existing "search then validate against held-out data" pattern anywhere in this codebase to extend. This is genuinely new capability, not a small addition, and is **explicitly deferred to a follow-up phase**, not Phase 57.

### Claude's Discretion
- Exact new-method name and signature (e.g. `generate_subsample_pair(...)`).
- Exact `transform_spec` key names for `type: "subsample_pair"` (D-05).
- Tier-gating mechanism for multi-seed averaging (D-07).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `_correspondence_idx` (Phase 56) already solves the hard part of this phase — tracking which output points map to which original-dataset points through a subsampling operation. The new method is largely "call `drop_points()` twice with different fractions/seeds on the same input, then optionally layer `generate_target`'s transform machinery on top" rather than novel index-tracking logic.
- `generate_target()`'s existing `transform_spec` dispatch (via `augment()`) already handles the "apply rigid/noise + optionally drop points" combination — the D-03 conditional-transform behavior may be expressible as a thin wrapper choosing whether to pass a transform-bearing `transform_spec` into the existing pipeline or skip straight to a plain subsample.

### Established Patterns
- Discriminator-key dispatch (`transform_spec["type"]`) is already the established pattern for `generate_target()` (D-04 extends this pattern rather than introducing a new one).
- Tier-based gating (`sanity`/`dev`/`full`) already exists for other budget-sensitive behaviors (e.g. `DEV_N_TRIALS`, `SOBOL_MIN_TRIALS`) — D-07's tier gate should follow the same convention rather than inventing a new mechanism.

### Integration Points
- `eval/runners/optimizer.py` has THREE separate `pipeline_mode == "synthetic"` branches (not one) — all three need updating consistently for `type: "subsample_pair"` to work correctly across sanity/dev/full tiers. This is a real risk area: missing one of the three branches would produce inconsistent behavior between tiers.

</code_context>
